# HalalCheck

HalalCheck is a static, multilingual ingredient screening PWA. Results describe available ingredient evidence, not a certification or a religious ruling. Unknown compounds, unspecified flavourings and source-dependent additives require verification. Product data can be incomplete or outdated: check current packaging.

## Development and QA

Use Node.js 24 LTS (Vercel-compatible; the QA runner imports TypeScript with native type stripping).

```sh
npm ci
npx playwright install chromium
npm run serve
npm test
npm run qa:100
npm run build
```

The local server listens on `http://127.0.0.1:4173`. `npm test` runs deterministic analyzer, product lookup and isolated database tests. `npm run qa:100` enforces at least 100 unit/integration executions, builds the deployment artifact, then runs desktop and mobile Chromium tests against `dist/` with the configured Vercel security headers. It writes `reports/unit.tap`, `reports/browser.json`, `reports/qa-summary.json`, `reports/i18n-coverage.json` and `reports/synthetic-analytics.json`. Browser tests use mocked external services; they never send analytics to production. Camera and install-prompt tests are simulations, not physical Android certification.

The database test uses in-memory PostgreSQL through PGlite with minimal Supabase Auth roles/schema fixtures. It executes every migration, sends 100 synthetic events through the actual Edge ingestion handler into PostgreSQL, checks aggregates, then checks additional rate-limit traffic, privileges and retention. It does not emulate the hosted Edge gateway, Supabase Auth service or pg_cron scheduling. No production credentials are needed.

## Public runtime configuration

`config.js` contains the public analytics URL. `admin/config.js` contains the project URL, publishable key and admin statistics URL. These public values are checked in; service-role keys and passwords must never appear in browser assets. Vercel serves the validated `dist/` directory generated by `npm run build`. The build deliberately copies only application assets, excluding tests, SQL, reports, dependencies and Git metadata.

The existing local product catalogue includes a physical-label yogurt fixture. Other barcodes use the [Open Food Facts product API](https://openfoodfacts.github.io/documentation/docs/Product-Opener/v2/products/get-product-by-code/). Matching barcodes are not evidence of certification. Community results are cached locally for at most 24 hours, bounded to 100 products, and always require current-label verification. API lookup sends the requested barcode to Open Food Facts; analytics never receives barcodes or ingredient lists. Open Food Facts data is available under ODbL: see its [reuse terms](https://world.openfoodfacts.org/terms-of-use).

## Supabase deployment (owner approval required)

Read migration history first. Never reset production or rewrite applied migrations:

```sh
npx supabase migration list --remote
npx supabase db push --dry-run --remote
```

On 9 November 2026, the linked production project reported both `20261031235000` and `20261104000000` as applied. The new migration `20261109000000_analytics_boundary.sql` remains pending and was validated in isolation. A dry run alone is not SQL execution validation.

After explicit owner approval, deploy the new ingestion function and migration together during a short maintenance window. The new handler requires the service-role RPC grant in the new migration; deploy the handler first (it temporarily rejects events until that migration is applied), then apply the migration. The old browser client remains compatible with existing event names. Never grant the ingestion RPC back to anonymous clients.

```sh
npx supabase secrets set HALALCHECK_WEB_ORIGIN=https://halal-check-sigma.vercel.app HALALCHECK_ADMIN_ORIGIN=https://halal-check-sigma.vercel.app
npx supabase functions deploy analytics-event --remote
npx supabase db push --remote
npx supabase functions deploy admin-stats --remote
```

Confirm CLI flags with the installed CLI version. `supabase/config.toml` disables gateway JWT verification only for anonymous analytics. The admin function requires a user JWT and independently verifies it with Supabase Auth, then calls the admin-authorized database function. See [Supabase function authentication](https://supabase.com/docs/guides/functions/auth-headers). Built-in server environment variables supply `SUPABASE_URL`, `SUPABASE_ANON_KEY` and `SUPABASE_SERVICE_ROLE_KEY`; never copy the last value into frontend configuration.

Create the owner securely in Supabase Auth and add only the intended UUID to `public.admin_users`. No registration UI is provided. Verify unauthorized and inactive accounts cannot access reporting. Production owner membership and login have not been verified in this run.

The migration registers a daily 03:17 UTC purge only when pg_cron is already installed. Otherwise schedule `select public.purge_old_analytics_events()` daily using a privileged operator job. Verify scheduling and monitor its execution; retention is not guaranteed merely by having a purge function. Reporting sessions are per-tab browser sessions, not unique people. The last-24-hours filter is rolling, and daily buckets use UTC.

The ingestion RPC enforces 60 events per session per minute. Sessions can be rotated, so this is not comprehensive bot protection; add gateway/network rate limiting if abuse warrants it. Client-side one-second event debounce is not transport idempotency: admitted repeated requests count separately. Analytics stores only allowed event names, session IDs, page category, language and device class. Metadata, referrer hosts and country values are discarded/rejected. Consent can be withdrawn through Privacy choices; existing aggregate records expire under retention.

## Vercel release and maintenance

Run QA and build, review the branch, then request owner approval before a production release. Preserve the current GitHub-to-Vercel integration; do not force-push. `vercel.json` configures `npm run build`, the `dist/` output and security/cache headers. Confirm these settings against the actual Vercel project before releasing; no Vercel account configuration was changed in this run.

After an approved release, verify the public page, both function URLs, owner sign-in, unauthorized rejection, real consented analytics and Android installation. Do not inject synthetic traffic into production. Confirm the new service worker activates and old `halalcheck-*` caches disappear. Admin pages and external services are not service-worker cached.

Maintain ingredient aliases with evidence and regression tests. Keep legitimate uncertainty visible and certification separate. `reports/i18n-coverage.json` lists untranslated English keys for each language; fallback coverage is not proof of complete localization. Arabic and Urdu use RTL text within a stable LTR application shell. Review translations with native speakers before claiming complete multilingual support.

## Current production release gate

See `HALALCHECK_RELEASE_REPORT.md` and `HALALCHECK_DEPLOYMENT_PLAN.md` for the latest release decision and exact approval scope. Read-only inspection is automated by `powershell -NoProfile -File scripts/release-evidence.ps1` and `node scripts/release-probe.cjs`. These require existing CLI authentication/network access but make no production data changes. `node scripts/release-verify.cjs` is the read-only **post-deployment** check; it does not submit valid analytics traffic.

The current release uses the tested Supabase SDK `2.119.0`, Node `24.x` and a clean allowlisted static build. Deno validation: `npx deno check --frozen supabase/functions/analytics-event/index.ts supabase/functions/admin-stats/index.ts`. QA exercises the actual admin Edge handler with mocked backend responses, plus the SQL boundary with real isolated PostgreSQL.

Production inspection found no Auth users, no active admin and no pg_cron installation. `supabase/maintenance/enable-retention.sql` prepares extension activation and the daily purge schedule; running it is a separate production change requiring approval. Owner creation/enrollment also requires an identified owner and separate explicit approval. Vercel secure login and project identity must be verified before frontend publication. Never use an unauthenticated temporary replacement deployment for this release.

The deployment plan supersedes the older example deployment order above: close the anonymous RPC boundary first, because neither function is deployed, then set origins and deploy the two functions. Do not enable a public ingestion grant as a rollback.
